# Sketch-thru-Plan JSON API

Sketch-thru-Plan (STP) provides a high-level [JSON-RPC](https://www.jsonrpc.org/specification) API that can be used to access services using languages for which an SDK may not be available.

## API access to/from STP

Events generated by client applications are normally forwarded to STP via Websockets. Other  mechanisms may be supported, in cases where STP is embedded in a larger server-side application that uses other communication mechanisms, for example event queues.

Sample code (in typescript) demonstrating how the standard STP Websockets connector is implemented can be found under [samples/typescript/connector-plugin](../typescript/connector-plugin).

Independently of the mechanism, communication with STP is required to be two-way, to provide ways for a client service to communicate events, such as user sketches and speech, but also receive events generated by other services, for example , events signaling that new symbols have been added.

## Outgoing message format

The JSON API mirrors the SDKs very closely. In fact, the SDKs offer a thin layer over the JSON API for convenience when using the services in javascript or .NET.

* method - Name of the event - same as used in the SDK
* params - Event parameters - same order and type as the SDK

```javascript
{
    "jsonrpc": "2.0",
    "method":"SendPenDown",
    "params":{
        "location": {
            "lat":58.95657852665255,
            "lon":11.175978030896498},
        "timestamp":"2020-10-27T20:50:30.584Z"
    }
}
```

## Returns

Most messages are `Informs`, and do not have any explicit return types. They update the state of the system, which may (or may not) result in some other component generating additional messages. For example, sketch and speech (separate) Informs may result in a new symbol being created or modified, which will be propagated via messages. If the sketch and speech could not be matched with high enough confidence though, no recognition messages are issued. Client's should therefore not rely on the generation of a response when Informs are used.

Queries are dealt with via `Requests`. These messages always produce a response, and are in this sense equivalent to a remote procedure call, even if the mechanism remains asynchronous. Results are provided in an array of objects. 

```javascript
{
  "id": 1,
  "jsonrpc": "2.0",
  "result": [
    {
      "fsTYPE": "coa",
      "poid": "id7J5ZJ1GVNQUNE"
      "name": "R1",
      "type": "hostile",
      "creator_role": "s2",
    }
    {
      "fsTYPE": "coa",
      "poid": "idADPSPP8Q29CGF"
      "name": "B1",
      "type": "friend",
      "creator_role": "s3",
    }
  ]
}
```

In case of an unsuccessful request, an error response is returned:

```javascript
{
    "jsonrpc": "2.0", 
    "id": "5",
    "error": {
        "code": -32601, 
        "message": "Invalid argument: expected a numeric id"
    }
}
```

## Incoming message format

STP components operate as both consumers and producers of events/messages. When connecting to STP, a component declares the events it is able to handle. STPs publish/subscribe mechanism then notifies components that are subscribed whenever relevant events occur. In the SDK, subscription is done automatically, based on the handlers the component instantiated before connecting to STP (see the [connector plugin discussion](../typescript/connector-plugin))

Incoming messages follow the same format as the outgoing ones, with a `method` property indicating the type, and `params` providing event-specific parameters. In the SDK, these corresponds to events the client subscribes to, prefixed with "on", for example `onSymbolAdded`. See the [javascript quickstarts](../../quickstart) for examples.

```javascript
{
    "jsonrpc": "2.0",
    "method":"SymbolAdded",
    "params":{
        "alternates":[
            {
                "fsTYPE":"unit",
                "poid":"idDS6X03AGXT68E",
                "creatorRole":"s3",
                "confidence":0.820098781593131,
                "alt":0,
                "sidc":{
                    "partA":"1003100015",
                    "partB":"1205010000",
                    "symbolSet":"10",
                    "legacy":"SFGPUCRVA--E---"
                },
                "location":{
                    "fsTYPE":"unit",
                    "shape":"point",
                    "coords":[{"lon":11.1648166167093,"lat":58.9486323288235}],
                    "width":0.0,
                    "altitude":0.0,
                    "radius":0.0,
                    "candidatePoids":[]
                },
                "shortDescription":"A/3-1",
                "description":"ARMORED CAVALRY RECON COMPANY",
                "fullDescription":"FRIENDLY ARMORED CAVALRY RECON COMPANY A/3-1",
                "affiliation":"friend",
                "echelon":"company",
                "parent":"3-1",
                "designator1":"A",
                "designator2":null,
                "status":"present",
                "modifier":"none",
                "strength":"none",
                "timeFrom":null,
                "timeTo":null,
                "altitude":null,
                "minAltitude":null,
                "maxAltitude":null,
                "extensions":{
                    "appId":"coaEditor",
                    "priority":3,
                    "metadata":{"color":"#FF0000","tags":["urgent","reviewed"]}
                }
            }
        ],
        "isUndo":false
    }
}
```

Note: `alternates` carries the primary interpretation plus any additional recognition
hypotheses (see `BuildSymbolAlternates` in StpJsonClient.cs); a single-element array is
the common case but clients should not assume exactly one entry.

## Extensions

All STP objects (symbols, tasks, task organizations, TO units, and TO relationships) support an optional `extensions` property that client applications can use to attach arbitrary additional data.

Extension values can be primitives, arrays, or nested objects - the full JSON data model is supported. The data is round-tripped through STP: values set when an object is created or updated (via `AddSymbol`, `UpdateSymbol`, `AddTask`, etc.) are persisted internally and returned on all subsequent events (`SymbolAdded`, `SymbolModified`, `TaskAdded`, etc.).

When no extensions are present, the property is omitted from the JSON payload.

### Setting extensions

Include the `extensions` property in the symbol or task object sent to STP:

```javascript
{
    "jsonrpc": "2.0",
    "method": "UpdateSymbol",
    "params": {
        "poid": "idDS6X03AGXT68E",
        "symbol": {
            "extensions": {
                "appId": "coaEditor",
                "priority": 3
            }
        }
    }
}
```

### Reading extensions

The `extensions` property is returned as part of the object in all notification events (e.g. `SymbolAdded`, `SymbolModified`), as shown in the incoming message example above.

## Schema

An [OpenRPC](https://github.com/open-rpc) definition of the api can be found in [sketch-thru-plan-api.json](sketch-thru-plan-api.json)

### Extensions to the OpenRPC spec

The contract uses these `x-`prefixed extensions beyond the base OpenRPC spec:

* `x-stpEvents` - the engine also sends unsolicited, asynchronous events to the
  client (`SymbolAdded`, `TaskModified`, etc.). OpenRPC has no native concept of a
  server-to-client push event, so these are listed separately from `methods` (which
  are client-to-engine calls) under this top-level key. Each entry has the same
  `name`/`description`/`params` shape as a method, but no `result`.
* `"x-descriptionStatus": "draft"` - marks a method or event whose description was
  generated from the engine source rather than hand-curated; treat the prose as a
  best-effort read of the C# rather than a settled, reviewed contract.
* `"x-engineDispatch": "none"` - marks a method that is listed in this contract (for
  example because an existing SDK still exposes it) but that the engine's
  WebSocketsBridge does not actually dispatch: the request deserialises with null
  params and is answered with a `RequestResponse` event carrying `success: false`
  ("No handler"). See the rule enforced by the STP repo's
  `tools/check-openrpc-surface.sh`, which fails a build if a contract method is
  missing from the engine's dispatch switch and not marked this way. No method
  carries it as of contract 0.6.0: the eight COA methods (`AddCoa`, `UpdateCoa`,
  `DeleteCoa`, `SetCurrentCoa`, `GetCoaContent`, `ImportCoaContent`,
  `SetCoaTaskOrg`, `ResetCoaTaskOrg`) that carried it until 0.4.0 are now
  dispatched (STP-1058).
* `"x-layer": "transport"` - marks a message that belongs to the wire protocol
  rather than to the application surface. Three carry it: the `Register` and
  `Request` methods and the `RequestResponse` event. Every SDK builds and consumes
  these inside its connector, so an application using an SDK never sends or sees
  one - but a client written WITHOUT an SDK cannot work without implementing all
  three, which is why they stay documented here. **Generators, reference pages and
  tool listings that present a public API should skip this layer**; anything
  describing the wire itself must keep it.
* `"x-layer": "client"` - marks a method the SDK answers ITSELF, without sending
  anything to the engine (STP-1373). One carries it: `SearchSymbol`, answered from
  the symbol index the SDK loads (see [Symbol search](#symbol-search)). It is part of
  the application surface - present it like any method - but it is not a wire
  message: a client written without an SDK implements it locally or does without,
  and the engine answers it, if sent, as any unknown method. The STP repository's
  surface gate refuses this layer on a method the engine dispatches.
* `"x-stpSafety": "read" | "write" | "destructive"` - on every method (STP-1059). What a
  call can do to state, so a client knows which calls are safe to make without asking:
  * `read` changes nothing on the server (queries, conversions, replaying the scenario to
    the caller);
  * `write` changes the scenario or session in the way the call names (add, update,
    select, recognize, session settings, undo);
  * `destructive` can remove or overwrite data the call does not name one by one:
    deletes, loading or creating a scenario (replaces it), resetting it, every import and
    sync (an imported object REPLACES a resident one with the same poid), and pushing to
    an external C2SIM server (which can reset that server).
  MCP tool annotations map from it: `read` is `readOnlyHint`, `destructive` is
  `destructiveHint`.
* `"x-stpInform": true` - the method is fire and forget: the engine sends no result, and
  the outcome arrives as events (for example `AddSymbol` -> `SymbolAdded`). Every method
  has either a `result` or this marker.
* `"x-stpOpenWorld": true` - the call reaches a system outside STP (the C2SIM server):
  `PullC2SIMInitialization`, `PushC2SIMContent`.
* `"x-stpEmits": [ { "event", "when", "condition", "to" } ]` - on every method (STP-1059):
  the events that follow a call, so a client knows what to wait for. An empty array means
  the call produces no event (every `read` method except `JoinScenarioSession`, which
  replays the scenario to the caller). Each entry names an event from `x-stpEvents` and says:
  * `when` - `always`: follows every successful call; `if`: follows when `condition` holds
    (for example only on a real change); `may`: depends on the content or on recognition -
    an import sends one event per object, a sketch may produce several events or none;
  * `condition` - a short statement of when it is sent, present unless `when` is `always`;
  * `to` - `caller`: only the client that made the call; `session`: every client in the
    session, the caller included unless `condition` says otherwise.

  **A client receives an event only if it registered that event's name when it connected**
  (`Register`; the SDKs register the events the application has handlers for). An entry
  is not a promise to a client that did not register the event.
  `RequestResponse` (the answer to every wrapped `Request`) and general `StpMessage`
  warnings are not listed; `StpMessage` is listed on the methods that also announce a
  refusal with it. The entries describe the intended behaviour; where the engine does not yet deliver
  it, the method also carries `x-stpKnownIssues`.
* `"x-stpKnownIssues": ["STP-1078", ...]` - the method is affected by filed engine issues,
  by ticket key: today's engine may not deliver what its description or `x-stpEmits` says
  (for example an event that never arrives, or a call that times out although it worked).
  The key is dropped from the contract once the fix ships.
* `"examples": [ ... ]` - on every method (STP-1059): one OpenRPC example pairing taken from
  a live engine, not hand-written. `params` and `result` are what went over the wire; a
  fire-and-forget method's example has no `result`. Long values are abbreviated and the
  example's `description` says so. `PrologTerm`, the STP text each object of an object-set
  result carries, is left out of every example (STP-1085); the object-set examples' `description`
  says so. Each example can carry:
  * `x-stpEventsObserved` - the events the call produced, as `{ event, params }`;
  * a name ending in `(captured, not completed)` - the capture could not complete the call
    (it needs an external server, or a known issue stops it); its `description` says what
    came back.
* `"x-stpEdgeCases": [ { "when", "outcome", "message", "note", "wire" } ]` - what the engine
  did, on a live capture, with bad or unusual input (STP-1059): a missing or unknown poid,
  no active scenario, malformed content, an inform sent through `Request`, and so on.
  * `outcome` - `refused`: answered `success:false` with `message`; `announced`: an
    `StpMessage` carrying `message`; `ignored`: nothing came back, so check the result
    another way; `accepted`: the call went through, and `note` says what it returned or sent.
  * `wire` - present when the case was sent differently from the method's usual path
    (`request` for an inform sent through `Request`).

  These record behaviour, not intent: an `ignored` or surprising `accepted` case is often a
  filed defect, and the method then lists it in `x-stpKnownIssues`.

## Symbol search

`SearchSymbol` (STP-1373, `"x-layer": "client"`) lists the symbols whose names or spoken
phrases match a typed text, best first, from a **symbol index** the SDK loads - no engine
round trip. The index format is
[`sketch-thru-plan-symbol-index.schema.json`](sketch-thru-plan-symbol-index.schema.json)
(`stp.symbol-index.v1`): one entry per symbol with its 2525D and 2525C codes, name, spoken
phrases, placing gesture and default affiliation.

* **The index is not in this repository.** STP generates it from its symbol tables and
  ships it with STP; an SDK loads it from a path it is given, by default from STP's
  installation directory. Without one, `SearchSymbol` is an **error** naming the path,
  never an empty result.
* **STP serves it (STP-1383).** STP 5.11.2 and later answer `GET /symbol-index.json` on the
  WebSocket bridge's own port with the installed index. The response carries:
  - `ETag` (`If-None-Match` gets 304) and `Cache-Control: no-cache`;
  - `X-STP-Version` and `X-STP-Symbol-Index: stp.symbol-index.v1`;
  - CORS on this route only (STP setting `WebSocket:SymbolIndexCors`, default `*`).

  An STP with no index installed answers 404 with
  `{"error":"symbol index not installed","expected":"<path>"}`. The JS SDK derives the URL
  from the connection string: `ws://host:port` becomes `http://host:port/symbol-index.json`,
  and `wss:` becomes `https:`. `SymbolSearch.load()` with no URL uses the most recently
  connected connector's bridge, else `http://localhost:9599/symbol-index.json`. An older STP
  that does not serve the route is an error that says so, never an empty result.
* **Every SDK ranks alike.** The method's description states the ranking; the invented
  index [`symbol-search/fixture-index.json`](symbol-search/fixture-index.json) and the cases
  in [`symbol-search/cases.json`](symbol-search/cases.json) are what each SDK's tests run,
  and the reference ranking - STP's own Presenter search - is held to them in the STP
  repository.

## Call validations

[sketch-thru-plan-validations.json](sketch-thru-plan-validations.json) is a data-driven rule set
that a client evaluates around every state-changing call (STP-1064), so a call is either refused
before it goes out, with the reason, or its result is explained after it comes back - never a
silent failure. It sits next to the contract, names the contract version it was checked against
(`contractVersion`), and has a schema of its own:
[sketch-thru-plan-validations.schema.json](sketch-thru-plan-validations.schema.json). One rule
file drives every runtime's evaluator (the stp-mcp live server's first; the SDKs' later).
`test/contract.validations.vitest.ts` checks that every method, param path, event and event path
it names exists in the contract.

`methods` has one entry per write or destructive method the engine dispatches:

* `preconditions` - session state that must hold before the call. `activeScenario`: the session
  has an active scenario. Without one the engine accepts writes, creates the objects, and
  `HasActiveScenario` stays false. Every method requires it except `CreateNewScenario`,
  `LoadNewScenario` and `LoadNewScenarioFromObjectSet`, which create one.
* `required` - params without which the engine ignores the call and says nothing (for example
  `UpdateSymbol` without `symbol`). The contract marks no param as required, so these are listed
  here, each backed by an `ignored` case in the method's `x-stpEdgeCases`.
* `references` - params whose value is a poid that must name an existing object: `{ param, kind,
  required }`. `kind` is `symbol`, `unit` (a symbol whose `fsTYPE` is `unit`), `task`, `coa`,
  `taskOrg`, `taskOrgUnit`, `taskOrgRelationship` or `any`, or a list of them. `required: true`
  marks the poid that names the call's target. Since STP-1091 the engine refuses an update, a
  task org default or a COA switch whose target poid names no live object of its kind, and an
  `AddTask` `who` or an `AddTaskOrgUnit` `parentTO` that names none. It does not check the
  others: a delete of an unknown poid is ignored. Engines before STP-1091 ignore an update of an
  unknown poid, create a task for `UpdateTask` on one, and create an orphan task for an `AddTask`
  with an unknown `who`.
* `intent` - the events that prove the call did what it asked (V10, "diff intended vs actual"):
  * `expect` - the proof events. The default is the method's `x-stpEmits` entries with
    `when: always` (to the caller or the session), each given a matcher. Empty when the
    contract promises no event (then a request is confirmed by its answer alone, and a
    fire-and-forget call cannot be confirmed by events at all);
  * `other` - events that show the engine did something else than asked (for example
    `TaskModified` instead of `TaskAdded`). An event on an object an expected event already
    matched is a follow-on, not something else (`AddTask` sends `TaskAdded`, then `TaskModified`);
  * `acks` - events that show the engine handled the call without proving it was done
    (`InkProcessed` before `SymbolAdded`);
  * `unverifiable` - `{ issue, reason }`: a filed engine issue, still listed in the method's
    `x-stpKnownIssues`, holds the expected events back. Their absence is then reported as
    unverifiable with the ticket, never as "not done". No rule carries it since rule file 1.0.1:
    the task org relationship events (STP-1089) and `UpdateTask`'s `TaskModified` (STP-1080), which
    1.0.0 marked this way, are sent since those fixes, so a client of an older engine sees them
    reported as not done.
* `confirm` - destructive methods only: what the call destroys, for the confirmation a client
  asks the user for. `{path}` is replaced by that param's value, `{path.length}` by an array's
  length.

The matcher vocabulary is deliberately small:

* **Equality on dotted paths.** `match` maps an event path to a value:
  `{ "param": "<params path>" }`, `{ "item": "<item path>" }` (inside `forEach`) or
  `{ "value": <literal> }`. Numeric path segments index arrays (`alternates.0.who`). Strings
  compare without regard to case, because the engine changes the case of enum values (`S3` comes
  back as `s3`). A value that resolves to nothing - an absent param - does not constrain the match.
  Examples: `AddCoa` expects `CoaAdded` with `coa.name` equal to the param `coa.name`;
  `DeleteSymbol` expects `SymbolDeleted` with `poid` equal to the param `poid`; `AddTask` expects
  `TaskAdded` with `alternates.0.who` equal to `task.who`.
* **Count per item of a param array.** `forEach: "objects"` expects one event per item of that
  array, optionally filtered by `where` (`{ "fsTYPE": { "in": ["coa"] } }` or `notIn`). The
  object-set imports use it, so an import that applies 2 of 3 objects is reported as partly done,
  with the missing one named.
* **Any of.** `anyOf: [ {event, match}, ... ]` is satisfied by any one of them (an imported object
  arrives as `*Added`, or as `*Deleted` when it carries the deletion version).

`refusalMessage` says how the engine announces that it refused a fire-and-forget call: an
`StpMessage` whose message contains the method name in quotes (`'AddCoa' refused: ...`,
`Could not read 'AddTask': ...`).

An evaluator reports one outcome per call: `done`, `partial` (what was done and what is missing),
`not_done` (refused, or handled without the expected events), `other` (the engine did something
else), `unknown` (no answer and no event within the wait) or `unverifiable` (see above).
